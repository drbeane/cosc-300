# Week 4: Projects

**COSC-300/500 Applied AI Essentials** · 4D focus: Discernment

## What you will be able to do

- Set up a project with instructions, reference files, and project memory.
- Write project instructions that fit one body of work.
- Choose which files belong in a project's knowledge base.
- Explain when a project is better than a one-off chat.

## The problem a project solves

In Week 2 you learned that every new chat starts empty. For work that runs over weeks, that means repeating yourself: uploading the same syllabus, explaining the same assignment, restating the same preferences. Custom instructions and memory help, but they apply to **everything** you do, so you can't fill them with the details of one course.

A **project** is a persistent workspace around one body of work. What you put there is added to the context of every chat inside the project and stays out of chats elsewhere. Claude, ChatGPT, and several other products have a feature of this kind, and most call it a project.

## What a project holds

| Part | What it is | Example, for a research methods course |
|---|---|---|
| **Instructions** | Standing directions that apply to every chat in the project | "I'm a junior in PSYC 320. Explain statistics in plain language and show the steps. Use APA 7 for citations." |
| **Reference files** | A knowledge base of documents the model can draw on | The syllabus, the assignment sheets, four assigned articles, your lecture notes |
| **Project memory** | What the tool learns across the project's chats, kept separate from your other work | That your paper topic is sleep and memory, and that you've settled on a survey design |
| **Chats** | Many conversations, all sharing the above | One chat per assignment or per study session |

Project instructions work like the custom instructions from Week 2, with one difference: they are scoped to one body of work. That makes them the right place for the details that were poor candidates for your account-wide instructions.

## Writing project instructions

Good project instructions answer four questions:

1. **What is this project for?** The course, the paper, the job search, and what you're trying to get done.
2. **Who are you in it, and who is the audience?** Your level, and who reads what you produce.
3. **How should responses look?** Format, length, tone, citation style.
4. **What should the model do or avoid?** The rules of the work.

An example for a research paper:

> This project is for my senior seminar paper on the effects of remote work on early-career employees. I'm a senior business major. The audience is my professor, who is an expert, and the paper is due in six weeks.
>
> The attached files are the assignment sheet and the sources I've collected. When I ask what the research says, answer from those files and tell me which file each point comes from. If the files don't cover something, say so before drawing on anything else.
>
> I'm writing the paper myself. Give me feedback and questions. Don't write paragraphs for me unless I ask for an example. Use APA 7.

Notice that the instructions tell the model **how to use the files** and **what kind of help is wanted**. Those two lines prevent the most common problems with a project: answers that blend your sources with general knowledge without saying which is which, and a helper that rewrites everything you show it.

## Choosing reference files

A project's knowledge base is where the "ground it in sources" stage of this course begins. Some guidance:

- **Add what you'd want a helper to have read**: the assignment, the key readings, your notes, a sample of your writing.
- **Leave out what doesn't bear on the work.** Every file competes for attention. Twenty marginal PDFs make it harder for the model to find the passage that matters.
- **Use clear file names.** "Smith 2022 remote work survey.pdf" tells you and the model more than "download (3).pdf", and makes it easier to check which source an answer came from.
- **Prefer text the model can read.** A scanned page that is a photo of text, or a slide deck that is mostly images, gives the model less to work with than a document with real text. Week 5 looks at file types in detail.
- **Mind what you upload.** The privacy settings from Week 1 apply to project files. Don't add other people's personal information or material you aren't allowed to share.

When a project's files are small, the product places them all in the context. When they are large, it searches them and brings in only the passages that seem relevant to your question. The last topic this week explains that search, and why an answer can miss something that is in your files.

## When a project beats a one-off chat

| Use a project when | Use a plain chat when |
|---|---|
| The work runs across many sessions | You have a single question |
| You keep returning to the same sources | No files are involved, or just one |
| The same instructions should apply every time | Your account-wide instructions are enough |
| You want this work's memory kept apart from everything else | Nothing needs to carry over |

Typical projects: a course you're taking, a research paper, a job search (your resume, target postings, and tone preferences), a club you help run, an ongoing client.

A project doesn't remove the lessons of Week 2. Each chat inside it still has a context window, and a very long chat still degrades. Start a new chat within the project when the task changes. That's cheap, because the instructions and files come along automatically.

## Check that it works

After you set up a project, test it before you rely on it:

- Ask a question whose answer is in one of your files, and confirm the answer matches the file.
- Ask a question your files **don't** answer, and see whether the model says so or fills the gap from general knowledge.
- Ask for something your instructions rule out, and see whether they hold.

If a test fails, revise the instructions, the way you revised prompts in Week 2.

## Key terms

**Project**: a persistent workspace of instructions, files, and memory shared by multiple chats. **Project instructions**: standing directions that apply to every chat in one project. **Knowledge base**: the reference files attached to a project. **Project memory**: memory scoped to one project.
