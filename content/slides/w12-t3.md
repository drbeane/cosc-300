## An MCP server exposes

- **Tools**: actions the agent can take
  - `add_event`, `search_notes`
- **Resources**: data the agent can read
  - your course schedule, a dataset

The agent sees names and descriptions, just like skills.

---

## From last week's tool to a server

| | Tool in your program | Tool in an MCP server |
|---|---|---|
| Defined | Inside one program | In a separate server |
| Usable by | That program | Any app that speaks MCP |
| Who runs the loop | Your code | The app's harness |

Same round trip. The tool lives in another program.

---

## A tiny server, in outline

```python
@server.tool()
def next_class(course: str) -> str:
    """Return the next meeting time for a course."""
    return schedule[course]
```

The **docstring** is what the agent reads to decide when to call it.


---

## Designing a server

- **Few tools**, each with one clear job
- Descriptions that say **when** to use it
- Useful **error messages**
- **Read-only** unless the task needs more
- **Check the inputs**
- Return only what's needed

Least privilege, and now you're the one deciding.

---

## Test, then connect

1. **Inspector**: call each tool by hand
2. Add it to **Claude Code** or **Cowork**
3. Ask a question that should use it
4. Did the agent call the right tool with the right inputs?

> Claude's remote connectors connect from Anthropic's cloud; a server on your laptop needs a local route.

## Which half failed?

- Wrong result **in the Inspector** → the bug is in your code
- Works there, but the agent doesn't use it → the **description**

Then write questions that should trigger each tool, and some that should trigger none.
